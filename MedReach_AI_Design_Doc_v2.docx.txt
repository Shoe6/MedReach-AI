1. Introduction
Purpose:
MedReach AI is a web-based, multi-tenant SaaS platform that specializes in healthcare data intelligence for pharmaceutical and medical device companies. The platform's first module focuses on cleaning, standardizing, analyzing, and intelligently querying Healthcare Professional (HCP) datasets. Rather than positioning MedReach AI as a marketing automation system, we treat marketing campaign generation as one downstream use of the cleaned and analyzed data, not the core value proposition.
The core capability is transforming inconsistent, unvalidated, and outdated HCP records into an analytics-ready dataset that a non-technical marketing or sales operations professional can query in natural language and export to downstream systems including CRMs, marketing automation platforms, and business intelligence tools.
This document describes the software architecture, phased requirements, user experience design, database structure, development environment, non-functional requirements, and production plans for MedReach AI. It is intended to be used by all developers on the team as the authoritative reference for design and architectural decisions throughout the capstone build.


Goal: What problem is this solving?
Mid-size pharmaceutical and medical device companies rely on Healthcare Professional (HCP) databases to drive their marketing, sales, and clinical outreach. Those databases are almost universally dirty. Outdated records, duplicate contacts, retired physicians still active in the system, NPI numbers that have not been validated in years. Marketing teams have no accessible way to clean, understand, and act on that data without hiring a dedicated data analyst or paying six figures annually for enterprise software like Veeva or IQVIA.
MedReach AI closes that gap by delivering the data intelligence capability that enterprise platforms provide, at a price point and accessibility level that a two- or three-person marketing team can actually operate. Cleaned data can then flow downstream into whatever marketing, CRM, or analytics tools the customer already uses. The platform's first module handles data intelligence. Future modules may extend into marketing automation, CRM integrations, sales enablement, and business intelligence — but the data foundation comes first.


Existing Solution:
MedReach AI is not based on a previous project. There is no existing codebase or prior version. The concept was developed as part of the AI Software Development capstone process at Full Sail University. This is Version 2.0 of the design document, revised after the Week 3 architecture review to reflect a repositioning of the product toward data intelligence rather than marketing automation, and to add enterprise-grade sections around multi-tenant security, non-functional requirements, and failure scenarios.

2. Overall Description
2.1. Product Perspective
2.1.1. User Interface Hardware
MedReach AI is a desktop-first web application accessed through a standard browser. The primary interaction mode is keyboard and mouse. No touch screen, voice control, or gestural interaction is required or supported in Version 1.0. The application targets standard office workstations and laptops. Minimum recommended display resolution is 1280x720. No local software installation is required — the application runs entirely in the browser.


2.1.2. Hardware Interfaces & Memory Constraints
MedReach AI requires no client-side installation. All heavy processing runs server-side on the FastAPI backend. Client hardware requirement is any modern desktop or laptop capable of running Chrome, Firefox, Edge, or Safari at version 120 or higher. The server hosting the self-hosted Ollama AI model requires a minimum of 16GB RAM and preferably 8GB VRAM for GPU-accelerated inference, or 32GB RAM for CPU-only operation. The application occupies no memory on the end-user device beyond what the browser requires.

2.1.5. Database
MedReach AI uses Firebase Firestore as its primary database — a cloud-hosted NoSQL document database. Firestore is selected for its multi-tenant security rules (data is scoped at the database level preventing cross-company access), real-time sync capability, and native integration with Firebase Authentication. Firebase Storage is used for all raw CSV uploads and generated export files. See Section 6.4 for the complete document schema and Section 6.2 for the multi-tenant security model.


2.1.6. 3rd Party Data and APIs
API / Data Source
	Description and Usage
	CMS NPI Registry REST API
	Free public API at npiregistry.cms.hhs.gov/api. Real-time physician record validation. Queried by NPI number to confirm active licensure, specialty, and practice location. Rate-limited at 20 req/sec; system batches requests accordingly.
	Firebase Authentication
	Google Firebase Auth SDK. Handles user registration, login, password reset, JWT token issuance, and multi-factor authentication for all API requests.
	CMS Open Payments Database
	Publicly available annual CSV published by CMS. Contains physician-pharma financial relationship records for Sunshine Act tracking. Cached locally and refreshed annually.
	FDA Warning Letter Database
	Public structured dataset from FDA.gov. Contains examples of off-label promotional language cited in enforcement actions. Used as validation data for the compliance intelligence layer.
	Ollama Local API
	HTTP API exposed by the locally hosted Ollama server. FastAPI submits prompts to Llama 3 8B and Mistral 7B through this endpoint. No HCP data is transmitted to any external service.
	

2.2. Technology Selection Rationale
The following section documents why each technology in the MedReach AI stack was selected. The goal is to make architectural reasoning explicit rather than simply listing implementation choices.


Technology
	Selection Rationale
	React 18 (Frontend)
	Chosen for team familiarity, mature ecosystem, and strong support for real-time UI updates during long-running data processing jobs. Alternative considered: Vue 3, but team experience with React reduces onboarding overhead. Server-side rendering is not required because the application is desktop-first and gated behind authentication.
	FastAPI (Backend)
	Chosen because the data processing pipeline is Python-heavy (pandas, scikit-learn, Presidio, Ollama SDK), making Python the natural backend language. FastAPI provides async support for concurrent NPI API calls and Ollama inference without threading complexity. Alternatives considered: Flask (rejected — no async), Django (rejected — heavier than needed for API-only backend).
	Firebase Firestore (Database)
	Chosen for three specific reasons. First, native multi-tenant security rules enforce data isolation at the database level, not just in application code. Second, real-time sync eliminates polling for background job status updates. Third, tight integration with Firebase Auth simplifies JWT validation. Alternatives considered: PostgreSQL (rejected — would require building tenant isolation, auth integration, and real-time sync manually); MongoDB (rejected — no equivalent security rules layer).
	Firebase Authentication
	Chosen because it is included with Firestore, provides multi-factor auth, JWT issuance, and role claims out of the box. Custom claims are used to encode tenant ID and role, allowing security rules to enforce access without per-request database lookups. Alternative considered: Auth0 (rejected — additional cost, additional integration complexity, redundant with Firebase).
	Ollama + Llama 3 / Mistral (AI)
	Self-hosted open source models are a deliberate architectural choice, not a cost-saving workaround. Healthcare and pharmaceutical customers are extremely reluctant to send HCP or provider data to external LLM APIs due to compliance, data ownership, and vendor lock-in concerns. Running all AI inference locally is a commercial differentiator versus competitors built on OpenAI or Anthropic APIs. Alternatives considered: OpenAI API (rejected — data leaves platform), Claude API (rejected — same concern), fine-tuned proprietary model (rejected — training data and cost overhead not justified when pre-trained open models meet quality bar).
	Microsoft Presidio (PII Detection)
	Chosen because it is production-grade (used by Microsoft Azure), Apache 2.0 licensed, and detects 50+ PII entity types out of the box. Alternatives considered: rolling custom regex-based detection (rejected — brittle, requires ongoing maintenance); AWS Comprehend PII (rejected — requires sending data to AWS).
	scikit-learn (ML)
	Chosen for Isolation Forest outlier detection and K-Means / DBSCAN clustering. Industry standard for tabular ML in Python. Well-documented, stable, and fast enough for datasets in the 10K–1M row range. Alternatives considered: XGBoost (rejected — overkill for clustering and unsupervised anomaly detection); custom clustering (rejected — no benefit over battle-tested library implementations).
	Vite (Frontend build tooling)
	Chosen for dramatically faster HMR (hot module reload) than Webpack, which speeds up UI development iteration. Native ES modules and lazy compilation reduce dev server startup from 30+ seconds (Webpack) to under 2 seconds.
	Recharts + Chart.js (Visualization)
	Recharts for React-native charting integration; Chart.js for chart types Recharts does not support well (heat maps, radar). Both are free, well-maintained, and produce accessible SVG output. Alternative considered: D3.js directly (rejected — steeper learning curve, longer development time for standard chart types).
	Tailwind CSS
	Chosen for utility-first approach, small production bundle after purge, and consistent design token enforcement across the team. Alternatives considered: styled-components (rejected — runtime CSS-in-JS adds bundle weight); CSS Modules (rejected — team preference for utility-first).
	ReportLab (PDF Generation)
	Chosen because PDF audit reports require precise layout control (letterhead, tables, page numbering) that HTML-to-PDF converters handle inconsistently. Programmatic PDF generation via ReportLab produces reproducible, pixel-consistent output regardless of server environment.

3. Specific Requirements
3.1. Milestones (Phased Delivery Model)
Following the Week 3 architecture review, the MedReach AI feature roadmap has been reorganized into three functional phases that better communicate the product vision. Each phase corresponds to a capstone milestone and maps to the historical MVP / Alpha / Beta timeline structure.
Phase A (Data Management) is the MVP and is required for the platform to function. Phase B (Data Intelligence) is the Alpha, layering AI-powered analysis on top of clean data. Phase C (Visualization and Export) is the Beta, exposing the analyzed data to end users and downstream systems. All features are written in user story format.


3.1.1. Phase A — Data Management (MVP)
Timeline: Month 2 of Capstone (Software Architecture). Focus: user authentication, dataset upload, data cleansing, duplicate detection, and record management. Without Phase A, no downstream analysis or visualization is possible.


● A1: The user will be able to register a new company account and log in securely using email and password authentication with optional multi-factor authentication.
● A2: The company administrator will be able to invite team members to their tenant and assign each member an Admin, Editor, or Viewer role.
● A3: The user will be able to upload an HCP contact list in CSV or XLSX format via a drag-and-drop upload zone with automatic column type detection.
● A4: The user will be able to review and confirm or correct the system's automatic column type detection before the cleaning pipeline begins.
● A5: The user will be able to view all PII detected in their dataset by Microsoft Presidio and choose to anonymize, remove, or override each flag.
● A6: The user will be able to review duplicate HCP records identified by the system and choose to merge, keep, or remove them.
● A7: The user will be able to view NPI Registry validation results identifying which records are active, inactive, invalid, or enriched with registry data.
● A8: The user will be able to review statistical outliers flagged in their dataset with a plain-language explanation of why each record was flagged.
● A9: The user will be able to view an audit log of every cleaning action performed on their dataset, with actor identity and timestamp.


3.1.2. Phase B — Data Intelligence (Alpha)
Timeline: Month 3 of Capstone (Project and Portfolio VI). Focus: AI-powered analysis, natural language querying, interactive exploration, and business insights on top of the cleaned dataset.


● B1: The user will be able to view AI-generated physician segments with plain-language labels and descriptions produced by the system.
● B2: The user will be able to ask questions about their dataset in natural language (e.g., "Show me all cardiologists in Florida with more than 500 prescriptions") and receive a filtered result set.
● B3: The user will be able to explore any segment interactively by drilling down into the record list, filtering, and adjusting segment boundaries.
● B4: The user will be able to receive AI-generated summaries and business insights about their dataset (e.g., top specialties, geographic concentrations, engagement patterns).
● B5: The user will be able to review compliance flags on any AI-generated content or export, including Sunshine Act relationships and state-level restrictions.
● B6: The user will be able to save frequent queries as reusable "views" for their team.
● B7: The user will be able to generate specialty-specific outreach copy for a selected segment as a downstream use of the analyzed data.


3.1.3. Phase C — Visualization & Export (Beta)
Timeline: Month 4 of Capstone (Software Integration). Focus: dashboards, charts, heat maps, reports, CSV exports, PDF summaries, and integration with external business platforms.


● C1: The user will be able to view an interactive analytics dashboard with charts showing segment breakdowns, data quality scores, and geographic distribution.
● C2: The user will be able to view a data quality heat map displaying record health across the uploaded database by field completeness and validation status.
● C3: The user will be able to download a PDF audit report documenting every cleaning action, flag, and resolution from their session.
● C4: The user will be able to export the cleaned and validated dataset as a CRM-compatible CSV file for downstream systems such as Veeva, Salesforce, or Mailchimp.
● C5: The user will be able to export a structured campaign asset package containing AI-generated content organized by segment.
● C6: The user will be able to view a summary report of engagement performance per segment when engagement metrics are logged back into the platform.


3.1.4. Version 2.0 (Post-Capstone)
Features intended for post-graduation development. Not part of the initial product planning and will not be assessed in Capstone.


● Direct two-way API integration with Veeva CRM and Salesforce Health Cloud for automated data sync
● Real-time HCP database monitoring with automatic scheduled re-validation against the NPI Registry
● Subscription billing and seat licensing via Stripe
● White-label client portal for marketing agencies to operate MedReach AI under their own brand
● Additional platform modules: marketing automation, CRM integration, sales enablement, business intelligence

4. User Experience
4.1. Use Cases (Sunny & Rainy Day)
Each use case is documented with a primary "sunny day" flow describing the expected successful path, followed by "rainy day" scenarios documenting how the system handles failures, edge cases, and recovery. This structure reflects enterprise expectations that a design document address not only what happens when things work but how the system behaves when they do not.


Use Case 1: New User Registration and Data Upload
Preconditions:
User has a company email address and an HCP contact list in CSV or XLSX format.
Main Flow (Sunny Day):
User navigates to MedReach AI and clicks Create Account. User enters email, password, company name, and industry type. Firebase Authentication creates the user credential; system creates a new company document in Firestore. User is assigned the Admin role and redirected to the Dashboard. User navigates to Upload Data, drags a CSV file onto the upload zone. System uploads to Firebase Storage, parses first rows for preview, and presents a column mapping interface. User confirms column assignments and clicks Begin Cleaning. Cleaning pipeline starts.
Rainy Day Scenarios:
● File exceeds 50MB size limit → upload rejected before storage; user is prompted to split file or reduce size.
● File format unsupported (e.g., .txt, .docx) → upload rejected; user is shown supported formats.
● File is corrupt or unparseable → upload accepted but parsing fails; user is shown the specific parse error (e.g., "row 47: unclosed quote") and offered a downloadable error log.
● Email domain already registered as an existing tenant → system suggests joining existing account rather than creating duplicate; user can request access from existing admin.
● Network drops during upload → resumable upload continues on reconnection; if not, user sees clear "upload failed" message with retry option.
● Firebase Auth is unavailable → user sees maintenance banner; login and registration are blocked until service is restored; existing sessions remain valid via JWT.
● Firestore write fails after Storage upload succeeds → orphaned file is cleaned up by scheduled cleanup job; user is prompted to retry.


Use Case 2: Data Cleaning Review
Preconditions:
HCP file uploaded, column mapping confirmed, cleaning pipeline has run.
Main Flow (Sunny Day):
User opens Data Review screen with four tabs: PII Flags, Duplicates, Outliers, Validation Errors. User resolves each tab by anonymizing, merging, or overriding flags. Data quality score updates in real time. When all tabs are clear, user clicks Proceed to Segmentation.
Rainy Day Scenarios:
● NPI Registry API is unavailable during validation → records marked as "unvalidated pending"; user can proceed with cleaning and re-run validation later; failed records are queued for automatic retry.
● Presidio detects PII in a required field the user cannot remove (e.g., name column) → user is offered anonymization (hash) rather than deletion; decision is logged in audit trail.
● Duplicate records span multiple uploads by different team members → system surfaces cross-upload duplicates and requires admin resolution.
● User accidentally marks all outliers for removal in bulk → confirmation dialog requires explicit acknowledgment; action is reversible from the audit log within 24 hours.
● Pipeline crashes mid-processing → partial results are saved; user is shown "processing incomplete" with option to resume; error is logged for engineering review.
● User attempts export before resolving all High-severity flags → export is blocked; user is directed to the specific unresolved flags.


Use Case 3: Segmentation, Natural Language Query, and AI Analysis
Preconditions:
Data review is complete. Cleaned dataset is ready. At least 50 records in the approved dataset.
Main Flow (Sunny Day):
User clicks Run Segmentation. System vectorizes records and clusters via scikit-learn K-Means. Llama 3 generates plain-language segment labels. User asks a natural language question in the query interface (e.g., "How many oncologists are in the Northeast?"). Llama 3 translates the question to a pandas filter and returns the result. User views AI-generated summaries and compliance flags on any output.
Rainy Day Scenarios:
● Dataset too small (under 50 records) → automated segmentation skipped; system offers manual grouping instead.
● Ollama service unavailable → user sees "AI temporarily unavailable" banner; non-AI features (data review, export) remain functional; queued AI jobs auto-resume on recovery.
● Natural language query is ambiguous ("show me the best doctors") → AI asks clarifying question rather than guessing.
● Query returns 0 results → user sees empty state with suggested query modifications, not a blank screen.
● Query is malformed by AI translation → system displays generated filter for user review before executing; user can edit or reject.
● AI-generated content triggers compliance flags → content is quarantined until reviewed; user cannot export until resolved or overridden with justification.


Use Case 4: Export & Downstream Integration
Preconditions:
Data review and (if applicable) compliance review complete.
Main Flow (Sunny Day):
User navigates to Export screen, selects Clean CSV / Campaign Asset Package / PDF Audit Report. System generates files; download links are presented and expire in 24 hours. Export event is logged with actor and timestamp.
Rainy Day Scenarios:
● Export exceeds 100MB → user is offered zipped download or chunked file split.
● PDF generation fails mid-render → user sees "report generation failed, retry"; error is logged.
● User's Viewer role attempts export → action is blocked at the RBAC layer; user sees permission-denied message with instruction to request access from admin.
● Downstream CRM import fails after export → not MedReach's failure, but export includes format documentation and troubleshooting guide.
● Firebase Storage quota exceeded (tenant limit) → oldest exports are auto-deleted after 24-hour window; user is warned when approaching quota.


Use Case 5: Administrative Actions & Team Management
Preconditions:
User has Admin role within the tenant.
Main Flow (Sunny Day):
Admin invites team member by email, assigns role (Admin / Editor / Viewer). Invitation email is sent via Firebase. Recipient accepts and is provisioned into the tenant.
Rainy Day Scenarios:
● Invited email is already registered under a different tenant → system blocks invite; recipient must leave existing tenant first.
● Admin attempts to delete their own admin account → blocked unless another admin exists in the tenant.
● Admin attempts bulk delete of records → confirmation dialog + admin password re-entry required for destructive operations.
● Admin loses access (locked out) → account recovery via verified backup email + support review; no direct data access without ownership proof.


4.2. User Characteristics
MedReach AI is designed for four specific user types within pharmaceutical and medical device companies. Each has distinct needs and pain points.


User Segment
	Age / Gender
	Role Description
	Marketing Manager / Director (Primary User)
	30–48, Mixed gender
	Day-to-day operator. Uploads HCP data, runs cleaning, reviews flags, queries the dataset in natural language, and exports results. Non-technical — needs the full workflow completable without writing code. Success is measured by time saved compared to manual spreadsheet work.
	Sales Operations Lead (Secondary User)
	30–50, Mixed gender
	Uses the analyzed dataset to align field sales rep territories with segmentation output. Primary concern is data accuracy and CRM format compatibility. Cares most about NPI validation and geographic segment data.

	Reviews cleaning results, manages RBAC assignments, validates compliance flags before export, and monitors platform usage. Cares about audit logs, non-functional requirements, and vendor security posture.
	Marketing Agency Partner (External User)
	25–45, Mixed gender
	Contracted agencies receiving HCP data exports from pharma clients. Need data that arrives standardized and validated for immediate use in their tools. Typically accesses the platform with Editor or Viewer permissions under the client account.
	

4.3. User Interface
The application is desktop-first, built on React with Tailwind CSS. A persistent left-side navigation panel is visible to all authenticated users. High-fidelity wireframes will be developed in the upcoming UX deliverable, covering both happy paths and error/recovery states as required by the architecture review.


Login and Registration Screen:
A clean centered card on a dark navy background. Email and password fields, Login, forgot password link, Create Account option. Registration collects email, password, company name, industry type. Inline field validation. Firebase handles all credentials.
Dashboard:
Post-login home screen with three summary metric cards — most recent upload row count, current data quality score, and open compliance flag count. A chart shows quality trends across recent uploads. Recent Activity feed lists the last ten team actions.
Upload Data Screen:
Drag-and-drop zone with format note. After upload: scrollable preview with AI-suggested column labels the user can override. Required columns must be mapped before Begin Cleaning is enabled.
Data Review Screen:
Tab-based layout: PII Flags, Duplicates, Outliers, Validation Errors. Each tab shows count badge and quality score progress bar.
Natural Language Query Interface:
Prominent search-style input at the top of the workspace. Users type questions in plain English. Results appear as a filtered table with the underlying generated query displayed for transparency and edit.
Segmentation Screen:
Grid of segment cards with plain-language names, record counts, top specialty badges, and geographic focus. Clicking a card opens a detail panel.
Analytics Dashboard:
Interactive charts — segment breakdown, geographic heat map, data quality trend, engagement history. All charts are drillable back to the underlying records.
Export Screen:
Three export option cards: Clean CSV, Campaign Asset Package, PDF Audit Report. Each shows contents, format, and estimated size. Export history table with 24-hour re-download window.

6. System Architecture
6.1. High-Level Architecture Diagram
The following diagram illustrates the MedReach AI system architecture at a component level. It shows the four primary layers — Client, API Gateway, Service, and Data — and the relationships between application components, AI services, databases, and external APIs.
  

Data flows from the React frontend through the FastAPI gateway (which enforces authentication, rate limiting, and tenant routing) into one of four service modules. All AI inference happens within the platform boundary — no HCP data is transmitted to external LLM APIs. The Data Layer enforces multi-tenant isolation via Firestore security rules.


6.2. Multi-Tenant Security Model & RBAC
Multi-tenant isolation is one of MedReach AI's most critical architectural decisions. The platform serves multiple pharmaceutical and medical device companies through a single instance. Under no circumstance may one tenant see or query another tenant's data. Isolation is enforced at three layers: the Firestore security rules layer (database-level), the FastAPI middleware layer (application-level), and the AI service layer (inference context isolation).
  



Isolation Enforcement Layers:
● Layer 1: Database layer: Firestore security rules validate the requesting user's tenant ID against every read and write operation. Cross-tenant queries are impossible at the database level, even if application code contains a bug.
● Layer 2: Application layer: FastAPI middleware extracts the tenant ID from the JWT on every request and scopes all database operations to that tenant. Attempts to specify a different tenant ID in the request body are rejected.
● Layer 3: AI layer: Each Ollama inference request runs in an isolated context. Model state is not shared between tenants. Prompts do not include cross-tenant data. This prevents information leakage through model behavior.


Role-Based Access Control (RBAC):
Every user within a tenant is assigned exactly one role: Admin, Editor, or Viewer. Roles are encoded as Firebase Auth custom claims on the user's JWT, which allows Firestore security rules to enforce permissions without additional database lookups.


Role Permission Categories:
● Category 1 — Data Management: upload files, resolve flags, delete records, invite/remove users. Requires Admin.
● Category 2 — Data Analysis: run cleaning pipeline, run segmentation, execute natural language queries, view AI-generated insights. Requires Editor or Admin.
● Category 3 — Data Export: generate CSV/PDF exports, download campaign packages. Requires Editor or Admin. Destructive operations (bulk delete) require Admin.
● Category 4 — Read-Only Access: query dataset, view segments, view dashboards, view audit log. Available to Viewer, Editor, and Admin.

7.2. Scalability & Stress Scenarios
The following scenarios document expected system behavior under enterprise workloads that exceed the single-user reference case. These help clarify how the architecture would need to scale beyond capstone scope.


Scenario 1 — Concurrent Uploads:
Multiple tenants uploading 100K+ row files simultaneously. Each upload runs its cleaning pipeline as a background job. FastAPI is stateless and horizontally scalable; adding worker processes increases concurrent capacity. Firestore handles concurrent writes via document-level transactions.


Scenario 2 — Concurrent AI Inference:
Multiple tenants running natural language queries and AI analysis simultaneously. Ollama inference is sequential per model instance. Solution: horizontal scaling of Ollama replicas behind a load balancer; requests distributed round-robin. Capstone scope: single Ollama instance; enterprise scope: 3–5 replicas per production region.


Scenario 3 — Large Dataset Export During Active Ingestion:
Tenant exports 1M-row CSV while a second team member uploads a new file. Export is a read-only operation on completed data; upload writes to a new upload document. No contention. Firebase Storage handles both operations concurrently.


Scenario 4 — NPI Registry API Rate Limit Exhaustion:
Multiple tenants validating large datasets in parallel could exceed the 20 req/sec NPI API limit. Mitigation: shared platform-wide rate limiter with fair queuing; per-tenant validation caching so repeated NPIs across tenants only hit the API once.


Scenario 5 — Cold Start / First Access:
Ollama model load time on cold start is 30-60 seconds. Mitigation: keep-alive on Ollama container prevents cold starts during business hours; first query at 3am may see slower response.


7.3. Reliability, Availability & Backup
Availability Target:
● 99.5% uptime (approximately 3.6 hours downtime per month) for capstone scope; commercial target 99.9%.
● Planned maintenance windows: Sundays 2am–4am ET; users are notified 72 hours in advance.
● Firebase services provide their own SLAs (99.99% Firestore, 99.95% Auth) — MedReach uptime is bounded by these.


Backup Strategy:
● Firestore automatic daily backups retained 30 days (Google Cloud managed).
● Firebase Storage exports auto-purge after 24 hours; source files retained 30 days for reprocessing.
● Audit log retained indefinitely for compliance.
● Tenant self-service data export available at any time via existing CSV export feature.


Failure Mode Handling:
● Ollama unavailable → non-AI features remain functional; AI features queue jobs and resume on recovery.
● NPI Registry API unavailable → validation marked pending; automatic retry on recovery.
● Firestore write failure → operation retried with exponential backoff; user notified after 3 failures.
● Storage upload failure → user prompted to retry; partial upload data cleaned up.


7.4. Maintainability
● Code style enforced via ESLint (frontend) and Black + Flake8 (backend). CI blocks non-conforming PRs.
● All external service integrations (Firebase, Ollama, NPI Registry) are abstracted behind interface layers to allow swapping without touching business logic.
● All environment variables (API endpoints, credentials, feature flags) are externalized to .env — no config baked into code.
● Every service module has an integration test that validates the public interface, allowing internal refactoring without breaking downstream callers.
● Deployment is automated via GitHub Actions — no manual production deploys.
